# 可信实时查看（首版）

## 范围

设备详情页展开“实时查看”可按 1 / 2 / 5 秒间隔查询快速指标、进程、Docker。
这是一条独立的设备双向连接，不以数据库的 `online` 或历史缓存作为目标可达的依据。
原有 HTTP 上报、离线遥测补传、分钟/小时历史和图表保持兼容，不将每秒的查看数据写入历史库。
首版采用浏览端按需 HTTP 查询 + Agent 标准 WebSocket RPC；不是浏览端连续推送订阅。
客户端仅在面板展开、当前页面可见、登录有效时查询，重复观看者共享同一设备/主题正在执行的请求。

## 连接与请求约束

- Agent 主动连接 `/api/agent/realtime`；它随机器服务管理的采集器运行，不依赖桌面窗口存在。
- 启动时以现有管理凭据向 `/api/agent/enroll` 登记独立设备密钥；登记只接受设备标识、安装实例 UUID、设备密钥。
- Hub 把设备标识绑定到安装实例与密钥哈希。另一实例不能覆盖同名设备。
- 同一身份（同一安装实例与密钥）的新连接会接管 Hub 尚未察觉断开的旧会话，旧会话的未完成查询立即以断开拒绝，不会被新会话完成；这样网络切换后不必等旧租约过期。60 秒内第 4 次接管会被拒绝（`device_session_conflict`），因为那说明同一身份正在两处同时运行（例如复制了 Agent 配置目录），不能让两份副本来回抢占。
- Agent 密钥只按设备标识保存在配置目录旁 `realtime/live-device-*.json`，权限 0600；改 Hub 地址（http→https、末尾斜杠、换域名）不会生成新身份。旧版本按"Hub 地址 + 设备标识"保存的 `live-*.json` 会在首次运行时被沿用。Hub 仅保存哈希于持久化 `data/agent-credentials.json`。目录与数据卷需要备份。
- 密钥文件损坏时失败关闭，不能自动清空信任或重建身份。复制整个 Agent 配置目录也会复制其身份，因此仍需妥善保护配置文件。
- 管理凭据轮换后，旧设备连接会在下一次心跳检查时断开；Agent 用新管理凭据重新登记同一设备密钥。管理凭据仍属于能够登记设备的管理员权限。
- 删除设备会移除其实时登记并断开会话，不保留吊销记录：Agent 仍在运行时会继续经 HTTP 上报、设备重新出现，此时它的实时连接也应能恢复，而不是永久失效。要让设备彻底消失，需要停掉该设备的 Agent。旧版本留下的 `revoked` 记录按"未登记"处理。
- 登记因安装身份不一致被拒绝（常见于重装 Agent 或删掉配置目录）时，Hub 在内存中记下时间，`GET /api/devices/:id/live` 返回 `identityConflictAt`，实时面板据此说明原因并提供"重置实时凭据"。重置调用 `POST /api/devices/:id/live/reset`（需登录，权限与删除设备相同）：删除登记并断开当前会话，下一次登记的安装实例被接受，Agent 最长约 30 秒内重连。
- 连接经过 hello / welcome / ready 后才接受查询。每次连接有新的 sessionId，Hub 不从 Redis/磁盘恢复活动会话。
- welcome 携带 Hub 的协议修订号 `revision`（当前为 2；缺省视为 1）。Agent 只在 Hub 声明支持后才发送新格式的结果；Hub 同时接受旧格式，两端可以分别升级。
- Agent 忽略不认识的帧类型；收到无法处理的主题只让该请求失败（`collection_failed`），不断开会话。
- Agent 侧的连接配置在文件变化时才重读；文件暂时不可读、为空或半写入时沿用上一份有效配置，不把一次读失败当成"配置已变更"而断开。常规上报循环使用同一套读取逻辑，不会因此把样本发往默认 Hub 地址或用占位密钥认证；只有配置文件不存在时才使用内置默认值。
- Hub 每 5 秒发送随机 challenge，只接受匹配的 pong 续期，租约 15 秒。握手最多等待 5 秒。租约用单调时钟，不依赖设备时间。
- 每个查询绑定 sessionId + requestId + topic，必须先 ACK，再返回通过 schema 校验的结果；单次查询截止 5 秒。
- 已知无有效连接立即拒绝；连接中断立即拒绝未完成查询。旧会话迟到结果、错误主题、未 ACK 的结果均不能完成新请求。
- 超时未 ACK 与已 ACK 未完成分别报告。TCP 写入成功不是应用交付成功，断网判定存在最长约一个租约的检测窗口。
- 实时请求绝不进入历史补传队列，重连后不重放。Hub 最多 256 个在途请求，按设备/主题合并；帧上限 4 MiB（按解压后计），发送背压上限 1 MiB。
- 完成的结果在同一会话内按设备/主题缓存 900 毫秒，期间所有观看者共用这一份；无论多少观看者、客户端轮询多快，设备端每个主题约每秒最多采集一次。失败不缓存。
- 结果未通过 schema 校验（如两端版本不一致）只让该请求失败（`invalid_result`），会话保留；格式错误的已知帧仍视为协议违规并断开，不认识的帧类型忽略。
- Agent 与 Hub 协商 permessage-deflate（4 KiB 以上压缩，无上下文接管）；Agent 写出超时按载荷大小放宽（约 64 KiB/s 起算，上限 10 秒），慢上行链路上的大列表不会因 2 秒超时把整条会话写断。
- 首版仅支持单 Hub 进程/副本。扩容前必须补齐会话归属、分布式租约与跨节点路由，不能直接横向复制。

## 数据真实性与负载

- CPU、内存、IO/网络速率按当前查询采集；首次尚无差分基线时相关指标标为不可用，不以零冒充。
- 实时快速指标（revision 2）使用独立的 CPU / 磁盘 / 网络差分基线，不拿上传采集的锁，也不触发慢探针。共享基线会把历史上报的平均窗口缩短成"距上一次实时查询"，让历史曲线随有没有人观看而改变。结果只含面板展示的 CPU、内存与四个速率，各自不可用时为 null，并遵守设备端的指标开关。
- 对 revision 1 的旧 Hub，Agent 仍按旧方式返回完整上报载荷（与上传共享采样状态），Hub 升级后自动切换到独立采样；Hub 收到旧 Agent 的完整载荷时会归约为同一份实时指标再交给浏览端。
- 普通 HTTP 上传交给异步网络写入者前冻结样本，不能让下一次采样修改正在发送的数据。
- 生产采集器将慢探针移至后台，快速数据不会等待整批硬件探针；慢任务未完成时不叠加启动。
- 温度、风扇、GPU、SMART 和硬件清单仍遵循现有慢采集及缓存频率，携带实际采集时间；首版没有把这些昂贵探针升级成秒级。
- 实时 CPU/内存曲线仅保留两分钟、最多 120 个点，缺失留断点；切换设备或会话不拼接旧会话曲线，切换查询间隔不清空曲线。
- 浏览端每个轮询周期只发一个请求：通道可用时直接读取主题；读取返回无连接后改为只查询连接状态，就绪后才再次读取，断开期间不会向设备发查询。
- 实时数据不写入客户端离线缓存。采集忙、超时、结果校验失败这类暂时性失败时，上一次结果继续显示并明确标注"N 秒前"，超过过期阈值（至少 6 秒）即移除；无连接、权限变化等其他失败立即移除旧结果。浏览端也检查请求耗时，拒绝严重延迟到达的响应。
- Docker 的网络与块设备列显示相邻两次查询之间的速率（同一 Engine、同一会话内计算，计数回退视为不可用），累计值放在提示里。

### 进程

Linux 基于 gopsutil 获取 PID、父 PID、名称、启动时间、CPU、RSS、线程数、状态；macOS 使用原生 sysctl + libproc 批量读取，不逐进程启动 `ps`，并检查权限失败后返回 null。
Windows 用一次 Toolhelp 进程快照取得 PID、父 PID、线程数与映像名，再逐进程以 `PROCESS_QUERY_LIMITED_INFORMATION` 读取启动时间、CPU 时间与工作集；不使用 gopsutil 的 Ppid/NumThreads（它们每个 PID 都重新拍一次全量快照，整体是 O(N²)）。
身份由采集实例 + PID + 启动时间组成，不只用 PID；无法读启动时间的受保护进程不作为可追踪对象展示。
CPU 使用累计时间差，按整机逻辑 CPU 容量归一化，首次为 null；不会宣称与所有系统工具每一列的口径完全相同。
最多读取 16384 个 PID，按 CPU、内存、PID 排序后返回占用最高的 4096 个（未知值排在已知值之后），并返回系统枚举总数与截断标记；页面每页最多 50 行。
首版不采集命令行、环境变量、逐进程网络/GPU、用户名，也不提供结束进程。

### Docker

只读取本机 Engine API 的 `/info`、`/containers/json?all=1`、固定容器 ID 的单次 stats。
Linux/macOS 支持 Unix socket（含当前服务账户可访问的 rootless / Docker Desktop socket），Windows 支持本地 named pipe。
`DOCKER_HOST` 仅接受本地 `unix://` 或 Windows `npipe://`，不接受任意 TCP/HTTP 目标；不跟随重定向。
没有 Docker、服务不可达、权限不足与确实零容器分开处理。容器名称不作为身份，使用 Engine ID + 容器 ID。
列表上限 512，最多为 32 个运行中容器读取资源统计，最多 4 个并发 stats 请求。运行中容器超过 32 个时，24 个名额给上次 CPU 最高的容器，其余名额轮换给最久未采样的容器，不让排在后面的容器永远拿不到统计；revision 2 的 Hub 会收到 `statsCandidates` / `statsRead` 说明本次覆盖面。
资源未读到时为 null；Docker CPU 按单核口径可超过 100%；内存与 `docker stats` 口径一致，扣除可回收的 inactive_file（cgroup v1 为 total_inactive_file）；网络/块 IO 为累计计数。
首版通过按需快照核对当前状态，尚未增加事件订阅、完整 inspect 详情、日志、启停或 exec。
Docker socket 本身通常拥有宿主管理权限，`:ro` 挂载不能提供只读 API 权限；不要向 Hub/Web 暴露 Docker socket。

## 入口、兼容与验证

Web 继续通过 Next.js 代理 `/api/**`；现有 Socket.IO 与 Agent 原生 WebSocket 使用独立的升级路由，不能互相接管连接。
外部入口、反向代理、FRP/NPS 需要允许 `/api/agent/realtime` 的 WebSocket Upgrade，空闲超时应大于 20 秒。
继承现有 `AGENT_REQUIRE_HTTPS` 策略；启用后必须使用 HTTPS/WSS（TLS 终止代理还需正确配置 `TRUST_PROXY`）。受信明文网络可沿用现有 HTTP 配置，不能在 URL 中放凭据。
Electron 通过主进程持有凭据并读取实时接口，preload 只暴露固定主题的只读方法；隐藏窗口不能继续驱动设备查询。
旧 Agent 继续 HTTP 上报，但实时面板显示未建立连接，不会把其历史 online 标志解释为实时能力。

自动化覆盖：会话失效/重连隔离、无连接拒绝、ACK/结果超时、凭据冲突/持久化/撤销、HTTP/WS 协议往返、Socket.IO 共存、Agent 心跳与采集隔离、重定向拒绝、Docker 权限与空列表、CPU 首次差分、前端会话与曲线断点。
真实设备验收仍需分别验证 Windows/Linux/macOS 权限、Docker Desktop/服务账户差异以及实际 NAS/穿透入口；不得以模拟测试冒充生产部署验收。
